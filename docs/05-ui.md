# User interface

The UI follows MVVM: all screen logic lives in the view model, and the markup only
binds to its properties and commands. The code-behind is empty — except for three
places where there is no other way.

## MVVM foundation

There is no ready-made library; instead there are four files in `Mvvm/`.

### `ObservableObject`

```csharp
protected bool Set<T>(ref T field, T value, [CallerMemberName] string? propertyName = null)
{
    if (EqualityComparer<T>.Default.Equals(field, value)) { return false; }

    field = value;
    Raise(propertyName);
    return true;
}

protected void Raise([CallerMemberName] string? propertyName = null) =>
    PropertyChanged?.Invoke(this, new PropertyChangedEventArgs(propertyName));
```

`Set` returns a `bool` — handy when something needs to be hooked onto the change:

```csharp
public PeriodOption SelectedPeriod
{
    get => _selectedPeriod;
    set { if (Set(ref _selectedPeriod, value)) { Reload(); } }
}
```

`Raise()` without an argument inside a setter fills in the name of that property — this is
how reverting a value in an input field works: the field is left unchanged, but we report
that it "changed", and the binding re-reads the previous value.

### `RelayCommand` and `RelayCommand<T>`

A plain `ICommand` implementation. Availability is re-evaluated **explicitly**, by calling
`RaiseCanExecuteChanged()`, not through `CommandManager.RequerySuggested`: this way it is
visible who enables a button and when.

```csharp
StartCommand = new RelayCommand(Start, () => _timer.IsIdle);
```

In the parameterized version availability depends only on the parameter's type, so its
`CanExecuteChanged` is an empty stub.

### `ITicker` and `DispatcherTicker`

```csharp
internal interface ITicker
{
    event EventHandler? Tick;
    void Start();
    void Stop();
}
```

The tick source is put behind an interface so that `TimerViewModel` can be tested:
in the application it is `DispatcherTicker` with a 100 ms interval, in tests it is
`FakeTicker`, which is triggered by hand.

The split comes out like this: **`TimeProvider` is responsible for "how much time has
passed", `ITicker` for "when to recompute the screen"**. The first is a domain question,
the second a UI question, and they should not be mixed up.

## View models

```
MainViewModel
├─ TimerViewModel      the timer and its buttons
├─ TodayViewModel      "today": hours, count, list
│   └─ SessionListViewModel
│       └─ SessionRowViewModel ×N
├─ StatsViewModel      period, chart, legend, list
│   ├─ SessionListViewModel
│   ├─ ChartColumnViewModel ×N  →  ChartSegmentViewModel ×M
│   ├─ GridLineViewModel ×N
│   └─ LegendItemViewModel ×N
└─ SettingsViewModel   durations, day boundary, type catalog
```

### `MainViewModel`

Knows which screen is open and distributes updates.

```csharp
public bool IsStatsVisible
{
    get => _isStatsVisible;
    private set
    {
        if (!Set(ref _isStatsVisible, value)) { return; }

        Raise(nameof(IsTimerVisible));
        IsSettingsOpen = false;
        ReloadVisibleScreen();
    }
}
```

The screen state is a **regular boolean property**, not the `Visibility` of some markup
element. In the markup it is turned into visibility by the stock
`BooleanToVisibilityConverter`.

`ReloadVisibleScreen()` reloads only the open screen. It is called when:

- a pomodoro has finished (`Timer.WorkCompleted`);
- the type catalog has changed (`Settings.CatalogChanged`);
- settings have changed (`AppSettings.Changed`) — for example, the day boundary;
- the window has been restored from the tray (`App.RestoreFromTray`);
- a query has run in the console (`ReloadAfterSql`).

`SqlConsoleRequested` is an event going up: the model does not create windows, `App`
takes care of that.

### `TimerViewModel`

A wrapper over `PomodoroTimer`: it holds a reference to the domain timer and turns its
state into strings for the screen.

```csharp
public void Advance()
{
    TimerStep step = _timer.Advance();

    if (step.Completed is WorkSession session) { WorkCompleted?.Invoke(this, session); }
    if (step.Event != TimerEvent.Nothing)      { PhaseFinished?.Invoke(this, EventArgs.Empty); }

    Refresh();
}
```

`Refresh()` is the only place where all visible properties are recomputed:
`TimeText`, `PhaseText`, `HintText`, `PauseText`, `Progress`, plus `IsWorking`,
`IsResting`, `IsPaused` and the availability of the three commands. When idle, it also
stops the ticker and shows the configured work duration on the dial.

Booleans `IsWorking`/`IsResting` instead of an enum property — so the markup has simple
`DataTrigger`s on `True`, without fiddling with type conversion in XAML.

The timer does not play sound: it raises `PhaseFinished`, and `Chime.Play()` is attached
to that event in `App`. This keeps the model free of side effects, so it can be created
in a test without worrying that it will start beeping.

### `SessionListViewModel` and `SessionRowViewModel`

Both screens use the same list: "today" without the date column, statistics with it.
The `ShowsDate` flag is handed both to the list and to every row.

`Load` carefully unsubscribes from the old rows before discarding them:

```csharp
foreach (SessionRowViewModel row in Rows)
{
    row.Changed -= OnRowChanged;
    row.DeleteRequested -= OnRowDeleteRequested;
}
```

A row **does not delete** from the database itself — it raises `DeleteRequested`, and the
owner (`TodayViewModel` or `StatsViewModel`) does the deletion, because after deleting
the screen also has to be reloaded.

Editing minutes lives in the setter:

```csharp
public string Minutes
{
    get => _minutes;
    set
    {
        if (!TryParseMinutes(value, out int minutes)) { Raise(); return; }

        string normalized = Format.Integer(minutes);
        if (normalized == _minutes) { Raise(); return; }

        _minutes = normalized;
        DurationSec = minutes * 60;
        _store.UpdateDuration(Id, DurationSec);
        Raise();
        Changed?.Invoke(this, EventArgs.Empty);
    }
}
```

Garbage and out-of-range values (0…1440) are silently reverted: `Raise()` without changing
the field makes the binding re-read the previous value. A dialog for every typo in the list
would be more annoying than a silent revert.

Fields in the constructor are assigned **directly, bypassing the properties**:

```csharp
// Assign the fields directly: going through the properties would look like an edit
// and would be written to the database on the row's very first render.
_minutes = Format.Minutes(session.Duration);
_selectedOption = Type.Length == 0 ? WorkTypes.NoTypeOption : Type;
```

This is not a matter of style but a fixed bug: in an earlier version a row whose type was
stored in a different case silently rewrote the history on the list's very first render.
The test `Showing_a_row_never_writes_to_the_store` covers this.

If a record's type is no longer in the catalog, it is still added to the list of options —
otherwise the selection could not be switched back.

### `StatsViewModel`

The largest model (about 300 lines), and almost all of it is spreading the result of
`StatsCalculator` over the collections the markup is bound to.

The legend behaviour is specified in words and implemented literally:

```csharp
public void ToggleType(string type, bool shiftHeld)
{
    List<string> allTypes = [.. Legend.Select(item => item.Type)];
    bool isShown = !_hiddenTypes.Contains(type);
    bool isOnlyShown = isShown &&
        allTypes.TrueForAll(other => WorkTypes.Comparer.Equals(other, type) || _hiddenTypes.Contains(other));

    if (shiftHeld)      { if (isShown) { _hiddenTypes.Add(type); } else { _hiddenTypes.Remove(type); } }
    else if (isOnlyShown) { _hiddenTypes.Clear(); }
    else                { _hiddenTypes.Clear(); _hiddenTypes.UnionWith(allTypes.Where(...)); }

    Refresh(rebuildList: true);
}
```

- a plain click keeps **only the clicked** type;
- a click on the only enabled type brings back **all** of them;
- Shift+click adds or removes **one** type.

Shift+click on the last enabled type hides everything: the screen shows zero hours
and "Nothing was worked in this period". This is left literal — the rule
"Shift toggles one type" has no exceptions.

The filter state lives **only in memory**: it is a view of the data, not a setting,
and after a restart everything is shown again.

The model finds out about Shift by itself:

```csharp
ToggleTypeCommand = new RelayCommand<LegendItemViewModel>(item =>
    ToggleType(item.Type, Keyboard.Modifiers.HasFlag(ModifierKeys.Shift)));
```

Yes, that is `System.Windows.Input` in a view model. The layer already knows about WPF
(it holds the brushes for the chart), and in exchange `ToggleType(type, shiftHeld)` itself
stays an ordinary method with a parameter — and is tested directly.

### `SettingsViewModel`

The three input fields (work, rest, day boundary) are exposed to the markup **as strings**,
because anything can be typed into a field:

```csharp
public string WorkMinutes
{
    get => Format.Integer(_settings.WorkMinutes);
    set => SaveMinutes(value, minutes => _settings.WorkMinutes = minutes);
}
```

Parsing, range checking and saving happen in the setter; the `Raise()` at the end either
normalizes the input (`007` → `7`) or reverts garbage. There is no scolding dialog: in an
earlier version one popped up on pressing "Start" if the field contained garbage; now
garbage simply never gets that far.

The type catalog is an `ObservableCollection<string>`, reloaded from the database after
every addition and removal. `CatalogChanged` goes up so that the open screen rebuilds the
option lists in the rows.

### Chart models

`ChartColumnViewModel`, `ChartSegmentViewModel`, `GridLineViewModel`, `LegendItemViewModel` —
immutable objects with `required` properties, recreated on every recomputation.
They need no notifications: it is not the object that changes but the whole collection.

`GridLineViewModel.Top` already includes the correction for half the label height — so the
number sits centred on the line rather than above it:

```csharp
Top = ChartLayout.GridLineTop(hours, scale, _plotHeight) - LabelHalfHeight
```

## Screens

| File | What it is |
|---|---|
| `Views/MainWindow.xaml` | the window: two screens toggled by visibility, and the settings popup |
| `Views/TimerView.xaml` | dial, hint, progress bar, three buttons |
| `Views/TodayView.xaml` | "today": hours, count, list |
| `Views/StatsView.xaml` | period, totals, chart, legend, list |
| `Views/SettingsView.xaml` | contents of the settings popup |
| `Views/SessionListView.xaml` | the shared record list for both screens |
| `Views/SqlWindow.xaml` | developer console |

### Switching screens

```xml
<Grid Margin="18" Visibility="{Binding IsTimerVisible, Converter={StaticResource BoolToVisibility}}">
```

Both screens sit in the same `Grid` on top of each other, and visibility is toggled by
a binding. The timer keeps running meanwhile: it lives in the model, not in the markup.

An important detail: visibility is set on the **wrapper**, not on `views:StatsView` itself.
If it is put on an element whose `DataContext` is changed right there, the visibility binding
starts looking for the property in the new context and finds nothing.

### Shared list

Column widths are defined **once** — via `Grid.IsSharedSizeScope` and `SharedSizeGroup`:

```xml
<ColumnDefinition Width="Auto" SharedSizeGroup="DateColumn" />
<ColumnDefinition Width="Auto" SharedSizeGroup="EndColumn" />
<ColumnDefinition Width="Auto" SharedSizeGroup="MinutesColumn" />
<ColumnDefinition Width="*" />
<ColumnDefinition Width="Auto" SharedSizeGroup="DeleteColumn" />
```

The header and all rows belong to the same groups, so they cannot drift apart.
In an earlier version the widths were hard-coded as numbers in four places, and changing one
of them broke the alignment.

The date column on the "today" screen is not just empty but `Collapsed` — a collapsed element
takes up no space, margins included.

The delete (trash) button appears when hovering over a row:

```xml
<DataTemplate.Triggers>
    <Trigger SourceName="RowRoot" Property="IsMouseOver" Value="True">
        <Setter TargetName="DeleteButton" Property="Visibility" Value="Visible" />
    </Trigger>
</DataTemplate.Triggers>
```

The row's root `Grid` has `Background="Transparent"` — without it, hovering is not detected
over the empty gaps between elements.

### Chart

Three layers in one `Grid`:

1. the caption "Nothing was worked in this period" — bound to `IsEmpty`;
2. the grid: an `ItemsControl` with a `Canvas` as its panel, position set via
   `ItemContainerStyle` → `Canvas.Top`; the layer is not hit-testable
   (`IsHitTestVisible="False"`), so it does not steal the columns' tooltips;
3. the columns: a `ScrollViewer` with horizontal scrolling and a `StackPanel` inside.

The scroll viewer's `Margin="36,0,0,0"` is the same `AxisWidth` as in `ChartLayout`.
This is the only place where the constant is duplicated: markup cannot use its value
directly.

### Legend

A chip is a plain `Button`, not a `ToggleButton`. The enabled state is drawn by a
`DataTrigger` on `IsShown`, not by the button's internal state:

```xml
<DataTrigger Binding="{Binding IsShown}" Value="False">
    <Setter TargetName="Chrome" Property="Opacity" Value="0.35" />
</DataTrigger>
```

A `ToggleButton` would flip its state by itself, before the model decides what to do with
the filter — and would show something untrue for a frame.

The command is fetched from an ancestor, because the chip's `DataContext` is the legend item:

```xml
Command="{Binding DataContext.ToggleTypeCommand, RelativeSource={RelativeSource AncestorType=ItemsControl}}"
CommandParameter="{Binding}"
```

### Settings menu

A `Popup` with `StaysOpen="False"`, bound two-way to `IsSettingsOpen`:
clicking outside the menu closes it and sets the property back to `false`.

Enter in the new-type field works without any code-behind:

```xml
<TextBox Text="{Binding NewTypeName, UpdateSourceTrigger=PropertyChanged}">
    <TextBox.InputBindings>
        <KeyBinding Key="Enter" Command="{Binding AddTypeCommand}" />
    </TextBox.InputBindings>
</TextBox>
```

`UpdateSourceTrigger=PropertyChanged` is mandatory here: without it, by the time Enter
is pressed the model does not yet know the typed text.

## Three exceptions

There is code-behind in exactly three places.

### Keyboard input

`SessionListView.xaml.cs` and `SettingsView.xaml.cs`:

```csharp
private void OnDigitsOnlyInput(object sender, TextCompositionEventArgs e)
{
    e.Handled = !Digits().IsMatch(e.Text);
}

[GeneratedRegex("^[0-9]+$")]
private static partial Regex Digits();
```

Filtering out non-digits is input handling, not logic. It is not validation either:
pasting from the clipboard does not raise `PreviewTextInput`, and pasted garbage is cut off
by the model. Enter in a cell clears focus (`Keyboard.ClearFocus()`), and the binding
with `UpdateSourceTrigger=LostFocus` fires on that.

### Chart panel size

`StatsView.xaml.cs`:

```csharp
public StatsView()
{
    InitializeComponent();
    DataContextChanged += (_, _) => PushPlotSize();
}

private void OnChartHostSizeChanged(object sender, SizeChangedEventArgs e) => PushPlotSize();

private void PushPlotSize()
{
    if (ChartHost.ActualWidth > 0.0 && ChartHost.ActualHeight > 0.0 && DataContext is StatsViewModel viewModel)
    {
        viewModel.SetPlotSize(ChartHost.ActualWidth, ChartHost.ActualHeight);
    }
}
```

`ActualWidth` is read-only, so there is nothing to bind it to the model with. Two handlers
rather than one, because the size and the `DataContext` arrive in an unpredictable order:
whichever event comes second hands the model the final size.
With only `SizeChanged`, the chart was once built with zero width
and stayed that way.

### Selection in the console

`SqlWindow.xaml.cs`:

```csharp
viewModel.Run(QueryBox.SelectionLength > 0 ? QueryBox.SelectedText : null);
```

`TextBox.SelectedText` is not a dependency property and cannot be bound.
F5 and Ctrl+Enter are handled here as well.

## Styles and themes

All colours are in `Themes/Colors.xaml`; there is not a single hex value in the markup.
Tokens are named by role, not by appearance:

| Name | Where it is used |
|---|---|
| `BackgroundBrush` | window background and framed input fields |
| `PanelBrush` | panel cards |
| `SurfaceBrush` | recessed areas: lists, the chart |
| `WellBrush` | the darkest: progress track, focused field |
| `ControlBrush` | flat buttons |
| `ControlQuietBrush` | top bar buttons |
| `ControlHoverBrush` | highlight under the cursor |
| `AccentBrush`, `AccentSoftBrush`, `AccentStrongBrush` | accent and its translucent variants |
| `RestBrush` | rest phase |
| `TextBrush`, `MutedBrush`, `BorderBrush` | text and borders |
| `ThumbBrush`, `ThumbHoverBrush`, `ThumbDragBrush` | scrollbar thumb |

The other dictionaries: `Text.xaml` (text and panel styles), `Buttons.xaml`,
`Inputs.xaml` (fields and drop-downs), `ScrollBar.xaml`, `Common.xaml`
(the visibility converter).

An important WPF subtlety: **a dictionary that uses resources from elsewhere must merge
them itself**. That is why `Text.xaml`, `Buttons.xaml`, `Inputs.xaml` and
`ScrollBar.xaml` begin with:

```xml
<ResourceDictionary.MergedDictionaries>
    <ResourceDictionary Source="Colors.xaml" />
</ResourceDictionary.MergedDictionaries>
```

Without it, a `StaticResource` inside the dictionary will not find the colour, even if
it is merged at the application level. Windows and screens are not subject to this rule:
they see everything in `App.xaml`.

The default `ComboBox` and `ScrollBar` styles are replaced entirely — the built-in light
ones look out of place in a dark theme.

## Accessibility

Buttons consisting of a single icon (gear, back arrow, trash) have
`AutomationProperties.Name` set: without it a screen reader would read out a character
from the Unicode private use area. The settings input fields and the console fields have
names too — which also makes them easy to locate in UI tests.
